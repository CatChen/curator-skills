# Game Curator manual testing

## Fresh-session activation gate

Before an independent evaluation, install the intended full commit using the [installation guidance](../README.md#install-and-try-game-curator). Start a new session outside the checkout, with no project-level skill masking the intended user-level installation. Confirm `$game-curator` (or `/game-curator` in Claude Code) is discoverable and actually selected; inspect the loaded path, symlink target or revision, and `SKILL.md`, references and scripts. Restart and resolve discovery if absent. Merely reading repository files is not activation; record the runtime, selected path and revision. Do not change a pre-existing installation without authorization.

These are procedures, not reports of passed tests. Use your own data only in user-controlled storage outside the repository. Do not include personal data or identifiers in public issue reports. Record runtime/version, browser, observed capabilities and state, acquisition method, collector result, counts, completeness, fallback and limitations for each test. Each collector is experimental and may need changes after live observation.

1. **Codex + Chrome:** install the skill, request `Diagnose Game Curator's Steam data acquisition capabilities in this session`, and use an authenticated Steam session only if available. Test library, wishlist, reviews and Replay separately, subject to the actual tool permissions. Save only authorized exports; validate and record warnings and discrepancies. Test manual export fallback if page-context execution is unavailable.
2. **Codex + IAB:** repeat the diagnostic and each source independently. Do not assume Chrome capabilities or authentication carry over. Sign in normally if needed. Record whether the IAB permits page-context execution, returning output or downloads; use DOM/manual fallback if not.
3. **Claude:** for the Claude Code desktop app's built-in browser follow [Claude Code](../skills/game-curator/references/claude-code.md) from a fresh session, record elapsed time, tool calls, `diagnostics`, the saver's decision and the replacement result, and run the four Node test files listed in that reference (the wishlist and library page scripts, the saver, and Codex orchestration) (the wishlist and library collectors have been run live in both Claude browsers, the library's resume only through a forced two-call test; the fresh-session acceptance procedures in those references are separate and are run by a reviewer in a new session). For Claude in Chrome follow [Claude in Chrome](../skills/game-curator/references/claude-in-chrome.md) from a fresh session (it needs a connected, signed-in extension and user approval for the download); the fresh-session acceptance for it has not been executed. Otherwise upload the packaged skill, verify activation, run the diagnostic and each feasible acquisition path, then exercise manual export/import fallback. Record actual permissions and any blockers.
4. **No browser:** supply an export or describe games and feedback in conversation. Ask for a personalized recommendation; confirm the answer distinguishes evidence and unknowns and does not claim an import occurred.
5. **Cold start:** say `My favorite games are Portal 2, Fez, and Outer Wilds. What should I play next?` Confirm useful advice arrives without mandatory onboarding, unsupported claims or spoilers.

For a source, first inspect the page and collector code, use the source-specific instructions in the skill, and compare the capture with what the page actually shows. Record visible count versus collected count if possible, and inspect missing fields. A zero result or scroll plateau does not establish completeness. On reviews, collect several pages and identify any missing pages; on Replay, discover available years and inspect each separately. Do not make account changes.

## Recovery scenarios

Run each scenario independently in a test runtime with synthetic data or a controlled mock; do not induce rate limits against Steam. Observe the agent's actual actions, not just its description. These scenarios have not been run as live agent tests.

| Simulated failure | Expected behavior |
| --- | --- |
| Stale URL | Rediscover the intended source in the same session, verify identity, and resume. |
| Adapter error, direct browser works | Probe the same session, identify the adapter as the failure, inspect and repair or adapt it, then validate records. |
| Changed selector | Inspect a representative row, change the temporary extraction strategy, test it and rerun. |
| Missing internal cache | Confirm the failure is specific to state access, then use a permitted scoped extraction or report partial coverage. |
| JavaScript unavailable | Use supported direct navigation and structured extraction or an export; do not attempt forbidden execution. |
| Empty or incomplete result | Verify account, membership and coverage, retain earlier batches and report uncertainty; do not call it success. |
| Authentication failure | Stop and request normal sign-in; do not request secrets or switch accounts silently. |
| Rate limiting | Stop requests, preserve batches, and report the limit without bypassing it. |

Also verify ordinary use leaves installed code and dependencies unchanged; in a separately authorized development session, verify that an agent fixes the source and adds a regression test where feasible. Record which checks are simulated and which were live.

## Persistence acceptance tests

These are acceptance procedures, not evidence that persistence has passed. Use a dedicated user-controlled persistent test directory outside the repository, with only synthetic game names and feedback as in [persistence examples](../skills/game-curator/references/persistence.md). Do not substitute a temporary cloud sandbox for a verified durable local home. Record runtime, actual location, permissions, explicit consent and scope, session boundaries, operations, expected and observed results. Do not paste private file contents into public reports. Restart the agent between sessions where indicated; a new message in the same session does not prove persistence.

| Case | Steps | Expected result |
| --- | --- | --- |
| First use, decline | Start with no test directory; request a recommendation using fictional favorites, then decline persistence. | Useful recommendation; no directory or files created; no forced onboarding. |
| Explicit opt-ins and discovery | In a fresh session, explicitly authorize profile/feedback and the durable settings record at the test path, declining raw cache. Give meaningful synthetic feedback and inspect files. Start a **new session with no prior conversation or platform memory**; use the conventional verified home or provide the custom path only, then ask a relevant question without requesting import or renewing consent. | With host permission, the agent reads `settings.json` first, verifies version 1 and both boolean scopes, and automatically reads relevant `profile.md`/`feedback.md`; it neither reads nor writes cache data when `steamCache` is false. Evidence is linked and no new opt-in is requested. If the custom path cannot be discovered, the user must supply it. |
| Revocation | After a valid opt-in, explicitly revoke profile/feedback or cache scope; test a later fresh session. | The agent stops using that scope immediately, records the changed choice when authorized and permitted, and does not delete personal files unless separately requested. A true stored value never overrides the current instruction. |
| Missing or invalid settings | With no record, malformed JSON, wrong version, missing/non-boolean fields, or extra fields, start fresh sessions and ask a question that could use persistence. Separately test a current question that needs no persistence. | No profile, feedback or cache content is read or changed based on invalid or missing settings. The agent asks for consent only when useful; otherwise it continues without persistence. Malformed files are preserved. |
| Feedback and correction | Provide one fictional observation, repeat it, then correct one detail in a later session. Inspect history and profile. Ask to edit or remove an entry. | One entry for the original observation, a distinct dated correction, correct evidence IDs and updated inference; explicit edit/removal is honored. No fabricated confirmation or replay of a user-deleted preference. |
| Cache reuse and explicit refresh | Separately opt in to raw caching. Save synthetic recent library/wishlist collector envelopes, start a fresh session, and ask a relevant question; then explicitly request refresh using a controlled source. | Relevant recent cache is read without a manual import or browser call; explicit refresh attempts the live source. Profile/feedback opt-in alone never authorizes raw caching. |
| Failed or incomplete refresh | Place a useful signed-in capture in the test cache; simulate failure and then a smaller public/partial capture. Compare original bytes before and after; permit a separate partial snapshot. | Original remains intact, stale/partial limitations are reported, and a useful partial snapshot is separate when authorized. No old wishlist is treated as current membership merely by union. |
| Identity, malformed data and conflict | Test unknown and differing account aliases; a malformed JSON cache; stale data; public versus signed-in scope; and a concurrent user edit to the profile between read and write. | Unknown/different identities are not silently merged, malformed data is not treated as empty or overwritten, stale/scope warnings remain visible, and conflicting edits are preserved or surfaced. No unsafe alias becomes a filesystem path. |
| Unavailable storage | Deny even the narrow settings-file read; separately simulate an unestablished location, read-only or ephemeral home. Ask for a recommendation and then give feedback. | No personal content is read on assumed consent. The agent asks when persistence is useful or continues without it; it reports permission or location limitations and makes no unverified persistence claim. Portable export is offered if useful and possible. |
| Replay split provenance | With cache opt-in, split a synthetic multi-year Replay capture containing diagnostics for all years into annual files. Include an unknown-year record. | Verified annual files contain only their year’s records; original multi-year diagnostics are retained with their scope clearly labeled or with the original capture context. Unknown-year data stays in a separate original capture. No annual file claims it contains every year. |
| Cross-runtime, conditional | Only if both Codex and Claude can actually access the same authorized persistent test path, write synthetic feedback in one and read it in a fresh session in the other. | Shared reads/writes are verified with actual content and permissions; otherwise mark cross-runtime persistence unverified. Never infer sharing from identical path strings. |

### Independent acquisition-to-persistence and learning checks

Run these in genuinely fresh sessions with the activation gate passed. Use synthetic collector results and a dedicated authorized test location; do not dictate the implementation steps in the test prompt. Record whether each operation was attempted, succeeded, denied, unavailable, or omitted, including sanitized errors and required approvals. A previous ad hoc successful save does not establish that the installed skill independently follows this workflow.

1. **Initial capture and cache:** Request acquisition and explicitly authorize raw caching. Exercise a supported direct destination and, separately where the host supports it, private staging plus approved transfer. Test a denied destination and a runtime without the proposed capability as distinct cases. Expect a synthetic probe when capability is unknown, complete collector objects retained outside page evaluation, no bulk data through model context, and final files read back and compared with the original in-memory results. Check parseability, source, timestamp, identity, scope, record count, coverage, warnings and diagnostics. Denial must not be bypassed and must preserve the existing cache; cleanup must not discard the only useful in-memory result.
2. **Fresh reuse and selective refresh:** Start another session with no prior conversation. Ask a relevant question and verify the authorized suitable cache is discovered and used without unnecessary collection. Explicitly refresh one source; verify only that source is refreshed and a failed or poorer result does not replace a richer capture. Check final data and provenance, not merely a claimed save.
3. **Unprompted learning:** After the initial recommendation, give a fictional game reaction, completion or abandonment status, purchase intention, and correction on ordinary follow-up turns without saying to save or reinvoking the skill. Verify dated feedback, appropriate profile reconciliation, preserved uncertainty and user-reported status even with absent or stale cache. Restart and confirm the observations inform a relevant recommendation, without presenting a completed game as new.
4. **No-op and conflicts:** Give an unrelated follow-up and repeat existing feedback; verify no unnecessary writes. Independently simulate concurrent edits and denied approval; verify edits survive, no success is claimed, and the user is told what remains unsaved. Test unknown playtime or achievements and confirm they are not described as zero or unplayed.

For each case also verify the exact files the agent read or wrote, the agreed consent scope, and whether it preserved unrelated user edits. Do not add a database, background process, or persistence script to make these tests pass.
