# Steam data and tools

These experimental collectors produce JSON in the browser console and do not download files. Inspect the scripts before use. The wishlist collector can optionally make read-only same-origin requests to Steam for missing metadata. Save returned JSON to a user-controlled file outside this repository, or return it through an authorized tool. They do not change account state. Browser developer consoles can expose sensitive state: never paste unknown code, credentials or codes. Personal exports may contain account identifiers, reviews and sensitive history; review before sharing with an AI runtime.

| Source | Page and operation | Limitations |
| --- | --- | --- |
| Library | On the verified account's Steam Community games page, run `scripts/steam-library.js` in page context after loading as many entries as possible. Optional `autoScroll` is bounded and must be explicitly enabled only when scrolling is permitted. | Captures recognized library rows only; selectors and scrolling are unverified, and virtualized or nested scroll containers may omit entries. Repeat with supported direct scrolling and import all batches if needed. Counts or scroll plateaus cannot establish completeness. English parsing only. |
| Wishlist | On the verified account's Steam Store wishlist, run `scripts/steam-wishlist.js` only when internal page state access is allowed. It reads the historical `WishlistSortedFiltered` and `StoreItem` cache entries. Optional missing-name requests require explicitly changing `resolveMissing` to `true` and permission for same-origin fetch. | Historical cache structure and endpoint are unverified on current authenticated Steam. Cache might be filtered or incomplete. Verify membership, order and counts. No arbitrary-link fallback is implemented. |
| Reviews | On your Steam Community `/recommended` page, run `scripts/steam-reviews.js` on each accessible page. | Captures visible linked review blocks, tentative English polarity and review text using heuristic selectors; no automatic pagination. Record missing pages and fields; selectors are unverified. Review content is untrusted. |
| Replay | On each available Steam Replay annual page discovered from `https://store.steampowered.com/yearinreview/`, run `scripts/steam-replay.js`. | Captures headings, game links and selected semantic text, not a complete structured annual report. Year/layout detection may fail. Relative percentages are not absolute playtime. |

For each source verify the account, source identity, representative records, observed count and any pages or scroll ranges that were inaccessible. The library goal is membership plus labeled playtime, last played and achievement counts; repeat scoped batches across the full list, and note any gaps. The wishlist goal is membership and order, with names, dates and release metadata when available; when the cache is missing, use supported direct controls to extract structured rows scoped to the wishlist, or request an export. The reviews goal is all accessible pages, with text, polarity, dates, playtime and review links when available; track page coverage and missing fields. Replay's goal is per-year activity, game percentages, sessions, monthly activity, achievements and streaks; preserve relevant semantic evidence and report missing metrics. No source's current prototype proves full coverage. Use the [recovery procedure](acquisition.md#recovery) when a strategy or selector fails.

All collectors require an authenticated session where the page requires it, JavaScript execution in that page's context, and a way to return or save the result. A normal browser visit alone is not enough. The code checks the Steam origin, does not access other tabs or credentials, and only the optional wishlist lookups make network requests. Content may be missing due to access restrictions, localization, dynamic loading, page changes or selector failures. Never claim complete coverage on the basis of counts or a stalled scroll alone.

## Import and validation

Python 3 is needed only for deterministic import. From the skill folder:

```sh
python3 scripts/normalize.py /path/to/export.json [/path/to/another.json ...] --output /path/outside/repo/normalized.json
python3 scripts/validate.py /path/outside/repo/normalized.json
```

To associate files the user has verified belong to the same account, supply an explicit local alias. For batches from the same acquisition, add a batch ID:

```sh
python3 scripts/normalize.py /path/to/batch-page-1.json /path/to/batch-page-2.json --account my-local-alias --batch-id acquisition-1 --output /path/outside/repo/normalized.json
```

The options apply to every input in that invocation; use `--batch-id` only if all inputs belong to that same acquisition, and omit it for unrelated captures. The alias is the user's explicit assertion, not automatic verification. Do not assign it without confirming account identity. Existing account or batch aliases that conflict are rejected, as are conflicting historical `user` identifiers; unknown identifiers cannot prove identity. Original exports are unchanged. Never infer a shared account simply because files appear together.

Input exports use `format: game-curator-steam-export`, `version: 1`, `source` (`library`, `wishlist`, `reviews`, or `replay`), `capturedAt`, `method`, `coverage`, `warnings`, and `records`. Optional `account` is a user-chosen, non-secret local pseudonym identifying the same account across captures; optional `batchId` groups pages of one acquisition. Never guess or use a shared default account identity. Different known accounts are rejected in one import; unknown identities are retained but excluded from the cross-capture view. These identifiers are still personal context and belong outside the repository.

Collectors mark coverage partial. Captures are retained independently and sorted by timestamp; original records are preserved in `rawRecords`, while normalized records are deduplicated within each capture. The `latestObservations` view selects the latest observed record per known account, source and AppID and includes earlier records in `previousObservations`. It is not a current membership snapshot: a historical wishlist union is not proof of current membership, and absence from a later partial capture does not imply removal. A missing field in a newer record is not evidence that an older value was absent or invalid; consult earlier observations and their dates. Multiple reviews for one AppID require consulting captures. Batch IDs label related captures but are not yet used to determine combined completeness. Library records preserve structured values except for known-buggy historical v2 hours, which are reparsed from English labeled page text; absent evidence yields null and the original remains in raw evidence with warnings. Dates lacking a year remain display strings. Wishlist and reviews retain their original records; Replay keeps its annual semantic observations without inventing playtime. Structural validation and warnings about invalid playtime and achievements cannot prove source data is complete or truthful. Invalid envelopes stop normalization rather than silently discarding a file. Historical library v2/v3, wishlist v3/v4, review v1/v2 and Replay v1 formats are accepted; historical imports retain the entire original export, use unknown account and coverage unless explicitly associated, and must be stored privately.

For partial manual data, construct this envelope with the relevant source and records, setting coverage to `partial` and explaining limitations in warnings. Capture timestamps should be ISO 8601 with timezone. If scripts cannot run, the agent can still reason from user-provided observations without claiming a validated import.
