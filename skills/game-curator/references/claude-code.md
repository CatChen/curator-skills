# Claude Code (desktop app): Steam wishlist collection

Use this when the session has the built-in browser tools (`mcp__Claude_Browser__*`: `navigate`, `javascript_tool`, `resize_window`, ...). It has tested collectors for the **wishlist, Library, Reviews and Replay** (the Replay section is below; see [acquisition](acquisition.md#recovery) for recovery). The Codex collectors need a `tab.playwright.evaluate` object that this runtime does not provide, so they cannot run here. Claude in Chrome uses the same script and saver with a different transfer; see [Claude in Chrome](claude-in-chrome.md). Claude Code CLI and other runtimes are best-effort recovery, not supported targets.

Files, all under `scripts/claude-code/` unless noted:

| File | Role |
| --- | --- |
| `steam-wishlist-page.js` | **Generated.** The standalone expression you paste into `javascript_tool`. Do not edit; run `node build-page-script.mjs` |
| `steam-wishlist-page.template.js` + `build-page-script.mjs` | Page orchestration (seek-scrolling, resume, bounds) and the generator that inlines the shared row code |
| `../browser/wishlist-rows.mjs` | Shared, self-contained row extraction and merge semantics used by this script **and** by the Codex `collectWishlist` |
| `save-capture.mjs` | Node saver: contract validation, cache policy, safe write and read-back |

## Procedure

1. **Consent first.** Raw cache writes need `steamCache: true` in the Curator Home `settings.json` ([persistence](persistence.md)); the saver checks it again and fails closed. Honor an explicit current instruction from the user over stored settings.
2. **Browser and pane.** Use the built-in browser and reveal its pane for the user (`mcp__ccd_view__show_pane` with `pane: "preview"`; navigating alone does not show it). Open `https://store.steampowered.com/wishlist/`. If a sign-in page appears, follow the sign-in hand-off in [recovery](acquisition.md#recovery): the user signs in normally, you wait, then verify and resume. Never handle credentials.
3. **Desktop layout.** The pane is about 700px wide by default and Steam then serves a reduced layout (no reorder handles or labeled fields). Call `resize_window` with width 1280, height 900, then reload. The script throws below 1000px. The emulation can be cleared when a turn ends; reset with `preset: "desktop"` when done.
4. **Verify identity and view.** The URL redirects to `/wishlist/id/<vanity>/`, but a URL alone does not establish whose account it is: ask the user to confirm the account and give their local alias for this capture, and never infer either from the URL, the persona name or an earlier capture. The script records the sort label and search-box state, but **not filters** (they sit in an Options panel it does not open), so `view.filters` is `unknown`. Matching item counts, equal records or an unchanged header total are supporting evidence only, never proof that no filter is active. Attest "no filters" (`--view unfiltered`) **only** after (a) directly inspecting the relevant controls with supported tools (open the Options panel and read the filter state, which changes only the page's view, and close it), or (b) the user explicitly confirms it for this capture. Otherwise omit `--view`: the capture is saved as a separate snapshot and does not replace or become the main cache.
5. **Run the collector.** Read `steam-wishlist-page.js` and pass its **entire text** as `text` to `javascript_tool` (`action: "javascript_exec"`). It registers `window.__gcWishlistRun` and runs (the file starts with `await`, which both browsers' tools accept). If it returns `{inProgress: true, ...}`, continue with the one-line call `await window.__gcWishlistRun({})` until the envelope arrives. Options go in the literal on the last line: `callBudgetMs` (35000, per call), `maxMs` (150000), `maxSteps` (1000) and `fresh`; `deliver` (`'return'` default, or `'download'` for tools that truncate large results, see [Claude in Chrome](claude-in-chrome.md)); `maxMs`, `maxSteps` and `deliver` are remembered across resume calls.
6. **Bulk transfer.** A full envelope is larger than the tool-result limit, so the runtime writes it to a file and returns its path (a JSON array of `{type,text}`). That native tool-result file is the only verified route: pass its path to the saver and never copy data through model context or retype it. If a small result comes back inline there is **no supported route to disk**: report that blocker, do not rerun the capture just to change how it is serialized, and do not pad the output to force a file (that would exploit an observed size behavior, not a documented transfer API). A user-supplied structured file (or `-` for stdin) is also accepted.
7. **Validate and save.**

   ```bash
   node <skill>/scripts/claude-code/save-capture.mjs <result-file> --provenance tool-result --account <alias> --access-scope signed-in --view unfiltered --dry-run
   ```

   Review the printed decision, then repeat without `--dry-run`. `--provenance tool-result` is the caller's statement that the file is the runtime's own tool-result file from this run; the saver never infers provenance from the file's shape, and without `--provenance` the capture is kept as a separate snapshot. `--account`, `--access-scope`, `--view unfiltered`, `--existing-account` and `--existing-view unfiltered` are **caller attestations**, not observations: pass them only for facts the user confirmed or you directly inspected for this capture (step 4); counts and record equality do not qualify. They are recorded in `diagnostics.attestations`, with the page's reported scope and a checksum of the original envelope, while the page's observed `diagnostics.view` and the rest of the evidence are kept as captured. `--existing-view` only fills evidence an older capture lacks; it never overrides a recorded non-default sort, active search or active filter. `--keep-separate` honors a user's decision not to promote. Use `--dest` and `--settings` for a user-specified custom location; the settings record must sit in a directory that contains the destination (symlinks resolved), and consent is re-read before anything is created and again before the commit. Then delete the tool-result file.
8. **Report** elapsed time, tool calls, `warnings`, `diagnostics` and the save decision, distinguishing live results from tests.

## What the saver validates and decides

It **rejects** (saves nothing) input that is not a valid v1 wishlist envelope: unexpected envelope or record fields (nothing is silently stripped), invalid `capturedAt`, `coverage`, `method`, `warnings`, non-positive AppIDs, empty names or `pageText`, wrong `membershipSource`, duplicate AppIDs or ranks, inconsistent counts, missing placeholder diagnostics, a records checksum that does not match the page's, a `signed-in` claim without the owner-only reorder-handle evidence, and zero rows without an empty-page observation, and anything that is not strictly a v1 wishlist envelope. It **keeps but never promotes** valid but incomplete captures as `wishlist.partial.<timestamp>.json`: a bounded stop, missing ranks, a count mismatch, and an **empty page**. Rows that never finished loading are **omitted** (never stored with blank or placeholder fields) and listed in `diagnostics.missingRanks`. A page showing 0 items is recorded as `empty-observed`, not as a verified empty wishlist, because an empty list has no owner-only reorder handles and the collector cannot independently verify the owner or filter state.

A capture becomes `wishlist.json`, by creation or replacement, only if its account and access scope are established (signed-in or public, with a verified account; `unknown` never qualifies) and it recorded the default sort, an empty search and caller-attested no filters. Replacement additionally requires: the existing file is structurally sound (valid required envelope fields, no duplicate AppIDs or ranks; older v1 files without newer diagnostics remain acceptable); same account, scope and coverage; strictly newer; the existing capture shows the same view evidence or the user confirmed it, and it does not record a conflicting one; no retained AppID lost a labeled field (release date, reviews, user tags, categories are checked individually, so a gained field never offsets a lost one); fewer than 5 `wishlist.superseded.*` backups exist; and the existing file is byte-identical at commit time as at decision time. A legitimately smaller unfiltered wishlist, or one with removed games, replaces. Otherwise the capture is saved beside it with exclusive creation. The previous file is preserved as `wishlist.superseded.<timestamp>.json` before a replacement. A lock file prevents concurrent savers. Nothing is merged and **nothing is ever deleted automatically**; at the backup limit the user decides what to prune. The final rename is not an atomic compare-and-swap, so the check narrows but cannot eliminate a race with an external editor; if the file changed, the capture is kept separately.

## Output contract

`game-curator-steam-export` version 1 with the same record fields as the Codex collector (`appid`, `rank`, `name`, `pageText`, `membershipSource`). `method` is `browser-dom-claude-code`; `capturedAt` is when the page script finished reading rows; `diagnostics.startedAt`/`finishedAt` bracket the acquisition. `account` and `accessScope` come from verified inputs at save time. `diagnostics` adds `complete`, `stopReason` (`complete`, `empty-observed`, `budget`, `no-progress`, `rows-missing`, `view-changed`), `missingRanks`, `view` (`sort`, `search`, `filters`, all observed), `recordsSha256`, timing counters and, after saving, `attestations`. Existing v1 caches stay readable, including ones without these fields.

## Shared code with the Codex collector

Row extraction (`snapshotWishlist`), merge (`mergeWishlistRow`: a loaded row is never replaced by a placeholder) and record shaping live in `scripts/browser/wishlist-rows.mjs`. They are self-contained functions because both hosts serialize them into a page: Codex passes the function to `evaluate`, and this runtime inlines its source into the generated script. Orchestration stays separate (Codex host-tab scrolling versus page-side seek, resume and file transfer). `collectWishlist` keeps its entry point and now reports placeholder rows instead of accepting them as loaded.

## Library (built-in browser; Claude in Chrome differs only in delivery)

Script: `scripts/claude-code/steam-library-page.js` (generated, with the shared row semantics from `scripts/browser/library-rows.mjs` and the shared page pieces from `page-common.mjs`). The Codex collector uses the same `snapshotLibrary`, `mergeLibraryRow` and `normalizeLibraryRecord`, so Steam-specific field rules have one source.

1. Consent, pane, desktop-width viewport and account confirmation are as above. Open `https://steamcommunity.com/my/games/?tab=all` and check it is signed in as the expected account.
2. Run the whole script with `javascript_tool` (it starts with `await`). In a measured session the 795 rows rendered progressively in about 2 s with no scrolling; the script waits (event driven) until the displayed "All Games (N)" count is reached and nothing changed for a quiet period (`quietMs`, 800 ms), and scrolls only if rendering stalls for `stallMs` (1500 ms), at most four times. Options: `callBudgetMs`, `maxMs`, `maxSteps`, `quietMs`, `stallMs`, `fresh`, `deliver`, `retainMs`. If it returns `{inProgress: true}`, resume with `await window.__gcLibraryRun({})`.
3. Save with `--provenance tool-result` (the result file) and `--account`/`--access-scope signed-in`. There is **no** `--view` for the library: its view evidence (`tab=all`, empty search) is observed. The saver writes `library.json`, `library.partial.*` or `library.superseded.*` with the same consent, replacement, field-loss and concurrency rules as the wishlist.
4. **Missing-value semantics.** Playtime, last played and achievements are parsed only from labels present in a row's own text by the one shared parser; the saver recomputes them from `pageText` and rejects any disagreement. An absent label is `null`, never `0`, and does not show that a game was unplayed (the page omits achievements for games without them, and the collector reports `rowsWithPlaytime`, `rowsWithLastPlayed`, `rowsWithAchievements` as informational counts). Labels are English only; a non-English page is warned about and, if its count cannot be read, the capture is not complete.
5. **Settling and views.** The collector counts a row as changed only when a game appears or its name, playtime, last played or achievements change; volatile client text (install size, `DOWNLOAD`/`UNINSTALL`/`UPDATE`) never resets the quiet period. The view (tab, search, count) is checked before any rows are merged: rows from a different view are never added to the batches already collected. After a second change the envelope keeps only the coherent batches and describes *them* (`view`, `expectedCount`, and `ownerControls` computed from the retained rows), while `diagnostics.viewAtStop` records where the page was; the capture is incomplete. A change of text inside an already active search is not observable.
6. **Older baselines stay separate.** A library cache written by the Codex collector (or any earlier capture) records no `account` and no `diagnostics.view`. The saver does not guess either, and the library has no attestation route for the view, so a new capture is saved as `library.partial.<time>.json` beside it until the baseline has that evidence (for example, after the Codex collector records the same view diagnostics). Passing `--existing-account <alias>` is only for a baseline the user has confirmed. In acceptance testing the new 795/795 capture was kept separate for exactly this reason and the existing `library.json` stayed byte-identical.
7. `pageText` also contains install state and sizes (`DOWNLOAD`, `UNINSTALL`, `UPDATE`, sizes), which change without any change to the library; do not treat them as data.

Live results (795 games): built-in browser 1 call, 0.9 s, 0 scroll steps, 795/795 through the native result file; the saver restored nested key order (the result file alphabetizes keys, including inside `achievements`, which first broke the records checksum). Compared with the Codex library cache from the previous day: 795/795 AppIDs, 0 added or removed, 0 differences in name, hours, playtime display, last played or achievements; `pageText` differed on 80 rows, 79 of them only in install size or button text. Live resume of the library was exercised with a forced two-call test (a 250 ms call budget, then `await window.__gcLibraryRun({})`), not with a collection that naturally exceeds the 45 s limit, since the page renders in about 2 s; longer resumes are covered by simulated tests.

## Reviews (built-in browser; Claude in Chrome differs only in delivery)

Script: `scripts/claude-code/steam-reviews-page.js` (generated; shared row code in `scripts/browser/review-rows.mjs`, also used by the Codex `collectReviews`). Unlike the wishlist and library, reviews are **paginated and every page is a real navigation**, so the script is a per-page step machine.

**What survives a navigation (measured in the built-in browser and in Chrome):** page JavaScript state does not; `sessionStorage` and `window.name` do. The collector carries its collected **data** in `sessionStorage` under one key, `gcReviews`.

**Trust boundary.** `sessionStorage` belongs to the site: any script on `steamcommunity.com` can read or change it. So the collector stores data only. **It never evaluates anything read from storage.** Each page re-runs the trusted bundled generated file (the host cannot keep our code on the page across a navigation, so it is pasted again for each page), and every field of the stored state is validated before it is used: shape and keys, version, list path, every page URL (same origin, same list, numeric page number, normalized), every review URL (the list's own account path and its appid), counts and sizes, option values and age. Malformed, foreign or expired state is discarded with a warning, replaced by a fresh run from the current page, and can never choose a navigation target. Data that passed through site storage is only as trustworthy as that origin; the envelope says so.

1. Open `https://steamcommunity.com/my/recommended/` signed in as the expected account and confirm the account with the user. Run the whole generated file with `javascript_tool` (it starts with `await`). Pass `({deliver: 'download'})` when the result will be saved (see delivery below).
2. It returns `{status: 'continue', next: '<url>', ...}`. Navigate the tab to `next` and run the same generated file again; the navigation and the run can be sent as one `browser_batch`. Repeat until the final envelope or delivery summary arrives. A 32-review list (4 pages) took 4 runs.
3. **Interruptions.** If the tab did not move, the same request is repeated at most 3 times (`repeated: n`); repeats do not renew the state's progress time, and a fourth ends the run with a partial result (`navigation-failed`, unvisited pages recorded). If navigation lands on another valid page of the list, its rows are merged and the requested page stays pending. If the tab is on something that is not the reviews list (a sign-in redirect), the script throws and **keeps its saved data**; sign in, navigate to the requested page and run the file again. A displayed-count change mid-run restarts once from page 1 so batches from different counts never mix; a second change, or the tab landing on a different account's list, ends the run with only the coherent batches and `diagnostics.viewAtStop`. `maxPages` (20, at most 100) bounds the run.
4. **Expiry versus removal.** State is *ignored and discarded* when it is more than 10 minutes since its last progress or 30 minutes since it started, but only **lazily, the next time the script runs**. Nothing deletes it on a timer, so an abandoned or crashed run leaves its data in that tab's `sessionStorage` until it is cancelled, discarded by a later run, finished, or the tab closes. A finished run removes the key. **To cancel:** on the originating tab run the same generated file with `({cancel: true})`, or run `sessionStorage.removeItem('gcReviews')`. Both touch exactly this collector's key (and delete, never read, a legacy `gcReviewsFn` key); no other site storage is ever cleared.
5. **Names are never observed:** the review boxes carry no game name (the capsule has no alt text), so records have none. The saver adds a name only with `--names-from <library capture>` from a library capture verified as the same account (matching `account` aliases, or `--library-account <alias>` for an older file the user confirmed). Enrichment is bound to the **exact snapshot**: the SHA-256 of the library file's bytes is recorded (a local digest identifies the file; it does not authenticate where it came from), every name is re-derived from that snapshot and must match, each is marked `nameSource: "verified-library-capture"`, and `diagnostics.attestations.enrichment` records the counts, capture time, account and digest. A page transfer that already carries names or attestations is **rejected**; a saved file with names but no matching attestation is invalid. A review whose game is not in the library stays without a name.
6. **Delivery.** A review set is small (32 reviews are about 15-17 KB). The built-in browser returns results of at least 40,000 characters inline and writes larger ones to a tool-result file, so a set this small has **no tool-result file**, and an inline result cannot be saved without retyping it: use `deliver: 'download'`. After initiating a download, look for the exact file name from the summary; if it does not appear promptly, **tell the user to check for a download dialog or permission prompt** (the built-in browser showed one that the maintainer had not expected, and an unattended dialog holds the file) instead of polling silently for a long time, and do not assume a prompt exists if you cannot see one. The finished capture stays retained on the page for authorized recovery without recollecting. Save with `--provenance download --page-summary '<summary JSON>'` as for Chrome ([Claude in Chrome](claude-in-chrome.md)); never pad output to force a file.
7. Saver: `reviews.json`, `reviews.partial.*`, `reviews.superseded.*`; view evidence is observed (`view.kind: recommended-list`, every page visited); owner evidence is the review controls; no `--view` attestation; `diagnostics.pagesVisited`, `pagesPending`, `pageAttempts` must be non-negative integers and consistent, and every review URL must belong to the collected list's account path. A baseline written by the Codex collector has no account or view evidence and stays separate, as for the library.
8. A public view omits reviews that are not public; the collector flags a view without owner controls. Review text is untrusted data: nothing in it is ever executed or interpreted (tested with hostile text).

Live results (32 reviews, 4 pages): the built-in browser's inline result had a `recordsSha256` equal to the SHA-256 recomputed over the observed fields of the Codex cache, i.e. identical records in identical order. Chrome and built-in browser downloads each matched their page summary (14,807 bytes) and are byte-identical in their observed records; names enriched from the verified library snapshot matched the Codex cache's names 32 of 32. The delay before a download appeared in the built-in browser (about 90 s) included an unattended dialog, so it is not a measured latency.

## Replay (built-in browser; Claude in Chrome differs only in delivery)

Script: `scripts/claude-code/steam-replay-page.js` (generated; shared extraction in `scripts/browser/replay-rows.mjs`, also used by the Codex `collectReplay`). Each annual report (`https://store.steampowered.com/replay/<account>/<year>`) is a real navigation, so the script is a per-year step machine that carries **data only** in `sessionStorage` under `gcReplay`, with the same trust boundary, validation, interruption handling, lazy expiry and cancel procedure as [Reviews](#reviews-built-in-browser-claude-in-chrome-differs-only-in-delivery): nothing read from storage is evaluated, every field is validated, the next navigation target is rebuilt from the validated account path and an integer year, and the trusted generated file is run on every year. Cancel with `({cancel: true})` or `sessionStorage.removeItem('gcReplay')`.

1. Open `https://store.steampowered.com/replay/` signed in as the expected account (it redirects to the newest report) and confirm the account with the user. Run the whole generated file with `({deliver: 'download'})`; navigate to each `next` and run it again (one `browser_batch` per year). Years come from links on the reports, visited in link order (2025, then 2022, 2023, 2024 for this account); `maxYears` (20, at most 30) bounds the run.
2. **The account path is the account's numeric Steam ID.** It is used inside the run to keep every year on one account and to build navigation targets, and it is **never written** to the capture, its diagnostics or warnings. Do not echo it into logs or commits. A different account appearing mid-run ends the run with only the first account's reports (`view-changed`, `diagnostics.viewAtStop.accountChanged`).
3. **Reports render in stages** (text, then game images, then counters and rank badges, with animation for a few seconds). The script reads a report only after its text and game-reference count have been unchanged for 1.2 s (at most 10 s) and keeps waiting while a `LOADING...` line is inside the text; a report that still contains one is flagged in the warnings and the saver keeps the capture as a partial snapshot. This matters: the existing Codex captures for two of four years contain a `LOADING...` line and a smaller text (its loading check only matches a text that is entirely the placeholder), so they are partial renders.
4. **Data semantics are preserved:** records are `{year, semanticText, apps: [{appid, name, source}]}`; `source` is `app-link` or `image-asset`, an image-asset AppID is a possible game reference and not proof of annual play, semantic text is unstructured, percentages are not hours, and `name` is whatever the page's own alt text or link text gave (often `null`). Duplicate AppIDs collapse with an app link beating an image asset. Coverage stays `partial`; `diagnostics.expectedCount` is the number of years discovered from links (visited plus pending), not a verified total of every report that exists.
5. **Saver, per year.** `save-capture.mjs` validates the whole capture (checksum, years, owner evidence: the page's own "Your Page Visibility" control on every report, view `annual-report`) and then writes one file per year under `<cache>/replay/` (`<year>.json`, `<year>.partial.<time>.json`, `<year>.superseded.<time>.json`), each deciding on its own with the shared policy. Every per-year file keeps the capture's metadata, carries `diagnosticsScope: "original-multi-year-capture"` so its counts and checksum are not mistaken for its own, and records `diagnostics.attestations.split` with a checksum of its single record. A file whose record does not match its split attestation is invalid. A legacy per-year file written by the Codex collector has no account or view evidence, so a Claude capture is saved beside it as a partial snapshot and the legacy file is never modified, replaced or migrated. Cache lifecycle changes and legacy migration are separate work.
6. Replay data is large for a Chrome result (about 27 KB for four years) and below the built-in browser's inline threshold, so use `deliver: 'download'` and save with `--provenance download --page-summary '<summary JSON>'`. After initiating the download look for the exact file name; if it does not appear promptly, tell the user to check for a download dialog or permission prompt rather than polling for long.

Live results (4 annual reports, signed-in account, same final script): built-in browser and Chrome each took 4 runs and 3 navigations, about 10 s in page, 27,337 bytes, complete; the two captures are identical in every record and their `recordsSha256` is equal. Against the existing Codex per-year captures: 2024 and 2025 are exactly equal (text and game references); 2022 and 2023 have the same AppID sets (13 and 21) with a fuller text, because the Codex captures were partial renders (a `LOADING...` line, fewer lines, and an alt-text name on one or two images that the finished page does not carry). A first built-in run with a shorter settle wait (400 ms) read 2022 to 2024 before their game images appeared (1, 2 and 2 references instead of 13, 21 and 16) and shows why the wait is a stable signature and not a single quiet read. A read-only production dry run decides `separate` for each year (the Codex files have no account evidence); nothing was written to the production cache.

## Observed runtime behavior (Claude desktop app, built-in browser)

Verified live on a signed-in wishlist of about 165 items, 2026-11-26.

| Capability | Result |
| --- | --- |
| `javascript_tool` runs async page code (loops, `await`, DOM reads, `crypto.subtle`, `MutationObserver`) | Verified |
| Page state persists between calls in the same tab | Verified |
| Per-call time limit | Restriction: a 100 s wait was cut off at 45 s. The script yields at 35 s plus bounded waits and resumes |
| Large results | A 60-70k-character result is written to a tool-result file whose path is returned; keys are alphabetized and an origin line is appended (the saver restores order and checks the checksum) |
| Pane default width | About 703px; Steam serves a reduced layout. Fix: `resize_window` 1280x900 and reload |
| Timers in an unfocused pane | `setTimeout` and `scheduler.postTask` with delay ran about 8x slow (about 1 s per wait) even with `visibilityState` "visible". A `MessageChannel` wait was accurate but measured about 50,000 messages per second, a busy loop. The script therefore waits on a `MutationObserver` and uses timers only as deadlines |
| Web Workers, `SharedArrayBuffer` | Blob Worker creation failed on this page; `SharedArrayBuffer` is undefined. Not used |
| Virtualized list | 14-26 rows exist at a time and re-render 0.1-1.8 s after a scroll. A fixed-step scroller skipped ranks 15-35; the script seeks the lowest missing rank and waits for the window to change |
| Lazy rows | Rows show placeholder text before loading; a row counts as loaded only when its app link has text |
| `tab.playwright.evaluate` (Codex collectors) | Not provided here |
| Local Node driving the browser; browser-initiated download | No supported tool found / untested. The tool-result file is the verified transfer |
| Steam filters (Options panel) | Not opened; unknown by design. Sort and search state are read |
| Empty wishlist, signed-out page, Claude in Chrome | Not exercised live (simulated or untested). An empty page is only ever recorded as observed |
| Consistency checks during a run | The page re-reads URL, count, sort and search at every collection boundary and checks rank-to-AppID and AppID-to-rank conflicts among observed rows. Changes confined to ranks never observed cannot be detected (stated in the envelope warnings) |

## If this collector fails

Treat it as an adapter failure, not a browser failure. Keep the session, inspect a representative row with `javascript_tool`, and follow the [recovery procedure](acquisition.md#recovery): adapt a temporary copy, validate counts, ranks and names, and preserve any partial capture (the saver keeps incomplete runs separately). Do not edit installed skill files during ordinary curation; report the failure instead. Without `javascript_tool`, use `read_page`/`get_page_text` with scrolling and the same validation, or an export.
