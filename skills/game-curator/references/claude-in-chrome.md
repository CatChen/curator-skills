# Claude in Chrome: Steam wishlist collection

Use this when the session has the Claude in Chrome tools (`mcp__claude-in-chrome__*`: `navigate`, `javascript_tool`, `tabs_context_mcp`, `computer`, ...) and the user wants Chrome (their real browser, already signed in to Steam) instead of the built-in browser. Scope is the **wishlist only**. It reuses the same generated page script, shared row extraction and saver as the [built-in browser path](claude-code.md); only execution and data transfer differ. Read that file for the saver's policy, flags, output contract and consent rules; they apply unchanged.

## Procedure

1. **Consent.** Cache writes need `steamCache: true` in the Curator Home `settings.json`. Downloading is a separate user approval: before step 5, tell the user the file name pattern (`gc-wishlist-<time>.json`), that it is generated by the page with no network request, its size (about 65 KB per 165 items) and that it holds their wishlist, and wait for a yes.
2. **Connect Chrome.** `list_connected_browsers` must list a browser; if it is empty, or `tabs_context_mcp` says "not connected", Chrome is closed or the extension is signed out or missing. Ask the user to open Chrome, click the Claude icon and sign in with the same account (install from the Chrome Web Store if absent), then retry. Load the deferred tools with one `ToolSearch` call. Use `tabs_context_mcp` with `createIfEmpty`, work in your own tab, and close tabs you created when done.
3. **Navigate and hand off sign-in.** `navigate` to `https://store.steampowered.com/wishlist/`. Chrome uses the user's profile, so Steam is usually signed in already; if a sign-in page appears, follow the sign-in hand-off in [recovery](acquisition.md#recovery). Never handle credentials.
4. **Verify account and view.** Account: ask the user to confirm the account and a local alias; the URL (`/wishlist/id/<vanity>/`) and persona name are not proof. Filters: the script records sort and search but not filters. Attest "no filters" only after direct inspection or explicit user confirmation: with `computer`, click **Options** (find its position with `javascript_tool`), read the panel (Platform, Type, Discount, Exclude, Deck, Related items, Price should all be at their defaults), click Options again to close it, and compare the header's Wishlist total with the list's "N ITEMS" as supporting evidence only. The viewport needs no change in Chrome (the window is desktop width); the script throws below 1000px.
5. **Run the collector with download delivery.** Pass the **entire generated script** (`scripts/claude-code/steam-wishlist-page.js`) as `text` to `javascript_tool` with the options literal `({deliver: 'download'})` on the last line. The file starts with `await`, which Chrome's tool requires (it returns `{}` for a trailing un-awaited promise). A 165-row list took about 1.6-2.0 s in one call. The result is a small summary: `file`, `bytes`, `fileSha256` (eight groups of eight hex characters), `records`, `complete`, `stopReason`, `elapsedMs`, `scrollSteps`, `view`. If it is `{inProgress: true}`, continue with `await window.__gcWishlistRun({})`.
6. **Check the file arrived.** The file is saved by Chrome to the user's Downloads folder. Confirm it exists with Bash and that its byte count matches `bytes`. If it is missing, see "Download limit" below: do not rerun the scrape, since a held download is released once the user allows it.
7. **Validate and save** with the saver, adding the transfer checksum:

   ```bash
   node <skill>/scripts/claude-code/save-capture.mjs ~/Downloads/<file> --expect-sha256 "<fileSha256 from the summary>" --account <alias> --access-scope signed-in --view unfiltered --dry-run
   ```

   Review the decision, then repeat without `--dry-run`. `--expect-sha256` makes the saver refuse a file whose bytes differ from what the page produced. Omit `--view` unless step 4's inspection or confirmation happened; the capture is then kept as a separate snapshot.
8. **Clean up.** The downloaded file is private staging that duplicates cache data. Tell the user its path and ask before deleting it; never delete anything else in Downloads. Close the tabs you opened.

## Download limit (verified restriction)

Chrome allowed the first automatic download from `store.steampowered.com` and then silently dropped later ones, with no error to the page or tool, including from a fresh tab and including after a real click delivered by `computer`. The dropped download was **held** and saved once the user approved automatic downloads for the site (the address-bar permission prompt, or `chrome://settings/content/automaticDownloads`). After approval, further downloads saved normally. Never change that setting yourself. If a download does not appear, ask the user to approve it and check again before rerunning anything.

## Capabilities, verified in Chrome (macOS, 2026-11-26) against the built-in browser

| Capability | Claude in Chrome | Built-in browser |
| --- | --- | --- |
| Connection | Extension must be signed in and connected; `list_connected_browsers`, `select_browser`, `switch_browser`; user's own profile and Steam sign-in | Always available in the desktop app; separate isolated profile, user signs in in the pane |
| `javascript_tool` per-call limit | 45 s (CDP `Runtime.evaluate` timeout) | 45 s |
| Page state between calls (`window.*`) | Persists | Persists |
| Result size | **Truncated at about 1,000 characters** (`[TRUNCATED]`); no file spill. A 64 KB envelope cannot be returned | Large results are written to a tool-result file whose path is returned |
| Result filtering | A long string that looks like base64, including a bare 64-character hex digest, is replaced by `[BLOCKED: Base64 encoded data]`; objects are returned as JSON | None observed |
| Trailing promise | Not awaited (`{}`); use a leading `await` | Awaited, and a leading `await` also works |
| Bulk transfer to disk | Page-generated Blob download to Downloads (verified, user approval needed, see limit above); not the result | Native tool-result file |
| Viewport | Real window, 1595px wide in the test, desktop layout | Default pane about 700px wide gives Steam's reduced layout; needs `resize_window` 1280x900 and is cleared each turn |
| Timers | Accurate (10x120 ms took 1.2 s) with another tab in front; tab reported visible and focused; `requestAnimationFrame` immediate | Throttled about 8x when the pane is unfocused; the script uses a `MutationObserver` for this |
| Lazy list | Same virtualized list, same script worked unchanged | Same |
| Steam sign-in | Already signed in (user's profile) | Needed a manual sign-in |
| `file_upload` | Uploads local files **into** a page; not a path out | n/a |
| Blob Workers, `SharedArrayBuffer` | Worker constructor exists, `SharedArrayBuffer` undefined; not used | Blob Worker blocked, `SharedArrayBuffer` undefined |

Untested here: `read_page`/`get_page_text` as bulk readers, `resize_window` on the user's window (avoid resizing their real window unnecessarily), live resume across calls in Chrome (state persistence is verified; the resume logic is covered by the simulated tests), a signed-out Steam session, other operating systems and Chrome profiles, and clipboard transfer.

Comparison with the latest production cache (built with the built-in browser): the same 165 records, 0 added or removed, rank, name and `pageText` identical for every row, same label counts and the same records SHA-256, although the layouts differed (1595px against 1280px). The production cache was not written.

## Architectural notes for other sources

- **Transfer is the browser-specific part.** Chrome's result channel is about 1 KB, so any collector that returns a full dataset needs a download (or another out-of-band route). Design collectors as "collect in page, then deliver", with `return` and `download` as delivery modes.
- Keep summaries below about 1 KB and avoid long hex or base64-looking strings in them.
- A leading `await` and results that are small and JSON-friendly work in both browsers.
- One download is the only safe assumption per site until the user approves more; batch a source into one file.
- Chrome's real tab has accurate timers and prompt rendering, so large sources are faster than in the unfocused built-in pane, but the 45 s per-call limit and resume design are still needed.
- Library, Reviews and Replay have not been tried in Chrome.
