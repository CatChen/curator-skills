# Acquisition and diagnostics

Inspect the host's actual tools, procedures and permissions. Report each capability as **supported and verified**, **available but not yet tested**, **requires authentication or permission**, **unavailable**, **failed**, or **unknown**. Distinguish existing local files, authenticated Chrome, in-app and isolated browsers, navigation, DOM/accessibility inspection, JavaScript evaluation, internal state access, same-origin requests, returning results, downloads, local files, local execution, public web and uploads. Browser access does not imply authentication, JavaScript, internal state, network requests or downloads. Never expose sensitive browser state in the report.

Use harmless, minimal probes permitted by the host: inspect tool descriptions, open a Steam page if authorized, check a visible sign-in indicator without capturing credentials, inspect a small DOM fragment, and test other capabilities only using their documented procedures and with permission. Do not download a library as a diagnostic. An untested operation is unknown, not unsupported. State which collectors' prerequisites are verified and which fallbacks are possible.

Select methods according to the task: reuse sufficiently recent exports; use appropriate official APIs or authenticated browser access; use a bundled collector only when its operations are permitted; use navigation and DOM inspection; use public information; or ask for a user-provided export. These are preferences, not a rigid sequence. A user can sign in normally. Never request passwords, cookies, tokens or Steam Guard codes, bypass security, alter account state, or send personal data to unrelated endpoints. Explain failures and continue with partial data. Avoid excessive browsing to avoid requesting an existing export.

The bundled collectors are browser-runtime modules: import them in the host's JavaScript runtime and pass a verified browser tab, following [data and tools](data.md). Their page evaluations only read DOM; scrolling and navigation use supported browser controls. Do not infer permission for internal state, page-side requests or downloads from read-only DOM access. The modules are experimental; selectors and access may change. If the host lacks a compatible runtime or browser controls, use supported DOM inspection, an export, or conversational evidence without fabricating unavailable data.

## Recovery

An exception or empty output is not proof the browser is unavailable. Perform these steps before declaring a blocker, unless a genuine permission, security, authentication or rate-limit restriction requires stopping sooner:

1. State the operation's intention: source and account, fields, visible actions, and coverage criteria. URLs, selectors, internal state and scripts are replaceable strategies. Preserve successful batches, failing stage and exact error after removing secrets and personal identifiers. Classify script, adapter, navigation, authentication, permission, page structure, rate limiting, parsing and semantic completeness separately.
2. Use the host's supported direct controls on the **same browser and account session** to reproduce intended visible actions: navigate, wait, inspect a representative record, and scroll or paginate when relevant and permitted. If a URL is stale, rediscover the source through legitimate navigation and verify its identity. Do not silently switch browsers or accounts. If direct control works, the session is usable even if a script or adapter failed.
3. Inspect the error, tool contract, current page and relevant code. Identify the smallest plausible correction, such as a selector, stale URL, signature, missing cache or serialization issue. Within authorized capabilities, adapt the operation or repair an ephemeral copy; run a minimal probe, check representative fields, then resume the affected acquisition. Direct extraction is a valid recovery only when it yields structured records and validates coverage, not just a few examples. In an authorized development workspace with suitable tools, add a focused regression test and fix the source.
4. Validate source and account identity, membership, representative field accuracy, observed counts and pagination/scroll coverage. A successful tool call, an empty array, a count match, or a scroll plateau alone does not establish completeness. Preserve partial results, continue independent sources, and report unknowns and discrepancies.
5. Bound retries and request rates; stop on actual access, permission or rate-limit restrictions, and ask the user to authenticate normally if necessary. After reasonable attempts, report the sanitized error, direct-control outcome, repair attempted, remaining coverage and specific intervention needed. Never bypass host restrictions or access controls.

Temporary runtime repair is encouraged; silent permanent self-modification is not. During ordinary use do not rewrite installed skills, add dependencies, change repository files, commit or publish without explicit authorization. Offer a sanitized maintenance report or proposed patch; verified non-executable observations may be stored in user-controlled storage only when authorized.
